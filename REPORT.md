# Итоговый аналитический отчёт (Лабораторная работа №1)

## 1. Резюме (Executive Summary)

В рамках работы спроектирован процесс разработки микросервиса «Расчёт корзины и скидок»: 
выбрана СУБД, настроены ветвление, защита baseline, CI-контроль качества, 
выполнено обратное проектирование legacy-алгоритма и подготовлен план code review. 
Основной результат — воспроизводимый Quality Gate, который не пропускает код 
с нарушениями в интеграционную ветку `develop`.

## 2. Сравнительный анализ технологий

### 2.1. Матрица принятия решений

| Критерий | Вес | PostgreSQL | MongoDB |
|---|---:|---:|---:|
| ACID-транзакции | 0.35 | 5 | 2 |
| Гибкость схемы данных | 0.20 | 3 | 5 |
| Производительность чтения | 0.15 | 4 | 4 |
| Стоимость владения | 0.10 | 4 | 3 |
| Экосистема и сообщество | 0.20 | 5 | 4 |
| **Сумма весов** | **1.00** | | |

### 2.2. Расчёт и обоснование выбора

**PostgreSQL:**  
0.35×5 + 0.15×3 + 0.2×4 + 0.15×2 + 0.15×4 = 4.35

**MongoDB:**  
0.35×2 + 0.15×5 + 0.2×4 + 0.15×3 + 0.15×4 = 3.30

Выбран PostgreSQL, так как для хранения баллов, промокодов и истории транзакций 
решающее значение имеют ACID-гарантии и целостность схемы. MongoDB уступает 
по этим критериям, хотя выигрывает в гибкости схемы.

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма

![UML Diagram](docs/uml_diagram.png)

**Выявленные запахи кода:**

- Магические числа (`15000`, `0.85`, `500`, `0.90`, `0.97`, `0.93`, `0.70`).
- Отсутствие валидации входа.
- Жёстко закодированные промокоды `"SUMMER"` и `"VIP"`.
- Смешение нескольких ответственностей в одной функции.
- Слабая тестируемость из-за ветвлений и побочных эффектов.

### 5.2. План code review

Подход: ревью сфокусировано на точности расчётов, защите от фрода и 
корректности применения скидок.  
Ссылка на открытый PR с планом: (https://github.com/HighSkillScama/lab1-comprehensive-Maximov2/pull/3) 
Ключевые критерии: отсутствие магических чисел, валидация входа, покрытие тестами > 80%.  
Эскалация: после двух итераций без согласия — к Tech Lead; после трёх — возврат в бэклог.

## 6. Заключение

Настроенные процессы снижают риск внесения дефектов за счёт: 
(1) запрета прямых пушей в `develop`; 
(2) автоматического flake8-гейта на каждом PR; 
(3) явного плана ревью с измеримыми критериями; 
(4) документированной логики скидок в UML-диаграмме. 
В совокупности это делает качество проверяемым, а не зависящим от «внимательности» отдельного разработчика.
